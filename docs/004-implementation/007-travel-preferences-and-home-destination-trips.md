# 선호 여행지 순위와 홈 동행 조회

## 선호 저장 모델

`user_recommendation_destination_preferences.preference_rank`는 사용자별 1~3순위입니다.
V30 마이그레이션으로 NOT NULL 컬럼, 1~3 CHECK, `(user_id, preference_rank)` UNIQUE 제약을 추가합니다.
기존 선호 데이터가 없는 환경을 전제로 하며 기존 마이그레이션을 수정하거나 임의 순위를 이관하지 않습니다.

여행지 전용 편집 화면은 `PATCH /api/v1/users/me/travel-preferences`를 사용합니다.
로그인 필수이며 성공 시 204를 반환합니다. `Content-Type: application/json`입니다.

| PATCH 필드 값 | 처리 |
|---|---|
| 생략 | 해당 목록의 기존 값과 DB 행 유지 |
| `[]` | 해당 목록 전체 삭제 |
| 값이 있는 배열 | 해당 목록만 전체 교체 |
| 명시적 `null` | 해당 목록의 기존 값과 DB 행 유지 |

`{}`는 변경 없이 204를 반환합니다. 두 목록을 함께 보내면 같은 트랜잭션으로 변경합니다.
배열 내부의 `null` 항목은 400으로 거절합니다. 이 API는 `application/json`을 사용하는 자체 부분 수정 계약이며,
`null`을 삭제로 해석하는 JSON Merge Patch와는 다릅니다.
여행지 순서만 바꾸는 요청 예시:

```json
{
  "destinationPreferences": [
    { "type": "CITY", "destinationId": 2 },
    { "type": "CITY", "destinationId": 1 }
  ]
}
```

이 요청은 여행지 2를 1순위, 여행지 1을 2순위로 저장하며 기존 날짜는 그대로 유지합니다.
`availableDates`만 보내면 여행지와 순위는 그대로 유지합니다.
날짜 항목은 `startDate`, `endDate`가 모두 필요하며 완전히 빈 편집 카드는 요청에서 제외합니다.

`destinationPreferences`는 입력 기준 최대 3개이며 배열 순서가 선호 순위입니다.
동일 국가·도시 중복은 첫 항목을 유지해 제거하고 1부터 연속 순위를 부여합니다.
국가와 해당 국가의 도시는 함께 설정할 수 있습니다.
사용자 행에 쓰기 잠금을 획득하고, null이 아닌 배열로 전달된 목록만 삭제 후 재저장합니다.
생략되거나 null인 목록을 읽어 요청에 합치지 않으므로 다른 필드의 변경을 덮어쓰지 않습니다.

여행 선호 수정은 PATCH 단일 API로 제공합니다. 전체 설정을 교체해야 하는 경우에도 두 목록을 함께 보내며,
필드를 생략하거나 null로 보내면 해당 목록은 유지됩니다.

`GET /api/v1/users/me/travel-preferences`의 여행지 항목에 `preferenceRank`를 추가하고 순위순으로 반환합니다.
설정 화면은 1·2·3순위를 표시하고 사용자가 정렬한 순서대로 저장 버튼에서 PATCH 요청을 보냅니다.
삭제 시 남은 항목을 1부터 다시 표시하며 새 항목은 마지막 순위로 추가합니다.
안내 문구는 ‘1순위 여행지의 동행 모집글을 홈에서 보여드려요’로 맞춥니다.
타인 선호 순위 조회는 후속 개발입니다.

## 홈 조회

`GET /api/v1/home/same-destination-trips`는 로그인 필수이며 기존 카드 배열 응답을 유지합니다.
1순위 도시 ID 또는 국가 코드에 일치하는 게시글만 조회합니다. 국가 선호는 해당 국가 전체 도시를 포함합니다.
2·3순위로 보충하지 않고, 최근 검색·인기 여행지로도 대체하지 않습니다.

기본 노출 조건과 모집 상태·오늘 경계·진행 중 여행 처리는
[홈 게시글 추천 공통 노출 조건](../001-policy/002-home-recommendation-eligibility.md)을 따릅니다.
나이·성별·성향 점수·신청·추천 패스 이력은 필터링하지 않습니다.
`createdAt ASC, postId ASC` 오래된 순으로 DB에서 최대 30개 후보를 조회한 뒤, 서비스에서 무작위 3개를 반환합니다.
후보가 부족하면 0~3개만 반환합니다. 요청마다 무작위 선택을 다시 수행하므로 새로고침하면 결과가 달라질 수 있습니다.
카드 장소는 도시명, 인원은 호스트를 포함한 모집 인원, 이미지는 게시글 대표 이미지이며 없으면 null입니다.

기존 메이트 추천은 순위와 무관하게 모든 선호를 OR로 적용합니다.
국가 선호의 도시 연관관계가 null이어도 필터 조회에서 누락되지 않도록 LEFT JOIN을 사용합니다.

## 프런트 상태 계약

| 상태 | 홈 개요 SAME_DESTINATION_TRIPS | 표시 |
|---|---|---|
| 비로그인 | enabled=false, LOGIN_REQUIRED | 기존 로그인 안내 |
| 로그인·선호 없음 | enabled=false, DESTINATION_PREFERENCE_REQUIRED | 여행지 설정 안내 및 버튼 |
| 선호 있음·후보 있음 | enabled=true, disabledReason=null | 최대 3개 카드 |
| 선호 있음·후보 없음 | enabled=true, disabledReason=null | 아직 모집 중인 동행이 없어요 |

홈 개요는 선호 존재 여부만 확인하고 게시글 수는 조회하지 않습니다.
비활성 상태에서는 섹션 조회를 생략합니다. 선호 없는 상태에서 직접 조회하더라도 200과 빈 배열을 반환합니다.
설정 저장·삭제·순서 변경 후 홈 개요와 섹션 데이터를 다시 조회합니다.
제목은 ‘선호하는 여행지가 같은 동행’을 유지합니다. 전체보기 API는 후속 범위입니다.
백엔드 배포와 함께 프런트에 새 비활성 사유 처리 및 선호 순서 편집을 반영해야 합니다.

## 검증

컨트롤러 테스트로 PATCH 생략·명시적 null의 유지 처리, 빈 배열의 삭제 요청 전달, 목록 내부 검증을 확인합니다.
DB 통합 테스트로 생략된 날짜·여행지 행이 실제로 유지되는지 확인합니다.
단위·DB 통합 테스트로 순위 범위, 입력 최대 개수, 중복 제거, 재정렬·제거, 동시 저장,
국가 선호 보존, 1순위 변경 반영, 오래된 30개 후보 제한과 무작위 3개 선택, 날짜 경계와 제외 조건을 확인합니다.
마이그레이션 파일은 H2 MySQL 모드에서 실행해 필수 값·범위·순위 유일 제약을 검증합니다.
운영 MySQL에 대한 직접 적용은 배포 단계에서 수행합니다.
