# 홈 섹션 조회 정책

## 목적

홈은 여러 데이터 원천과 선택 정책을 사용하는 독립 섹션으로 구성됩니다.
각 섹션의 조회 로직은 분리하되 API 계약과 운영 기준을 한 문서에서 관리해 정책 차이로 인한 복잡도를 통제합니다.

## 공통 조회 흐름

각 섹션은 필요한 단계만 사용하며 다음 순서를 기준으로 구현합니다.

```text
접근 가능 여부 확인
  → 후보 생성 또는 저장된 결과 조회
  → 섹션별 정렬·선택
  → 현재 상태 재검증
  → 사용자별 상태 반영
  → 반환 개수 제한
  → 섹션 응답 생성
```

- 홈 개요는 `enabled`와 `disabledReason`만 판단하고 실제 데이터 존재 여부를 조회하지 않습니다.
- 후보 조건과 정렬 방식은 섹션의 제품 목적에 맞게 정합니다.
- 캐시나 사전 계산 결과가 있어도 삭제·마감처럼 달라질 수 있는 조건은 필요한 경우 다시 검증합니다.
- 신고와 좋아요처럼 사용자마다 다른 값은 공통 후보나 집계 결과와 분리합니다.
- 다른 섹션의 후보로 부족한 결과를 보충하지 않습니다.

## 응답 계약

활성 섹션은 독립적으로 호출하며 한 섹션의 빈 응답이나 실패가 다른 섹션 응답에 영향을 주지 않아야 합니다.

| 응답 형태 | 빈 상태 처리 |
|---|---|
| 목록형 preview | HTTP 200과 빈 배열 반환 |
| 단건 조회 | 해당 API의 not-found 계약 적용 |
| 생성 상태가 있는 추천 | `GENERATING`, `SURVEY_REQUIRED` 등 명시적인 상태 응답 사용 |

목록형 섹션은 요청 파라미터로 홈 노출 개수를 받지 않고 서버 정책으로 최대 개수를 제한합니다.
후보가 최대 개수보다 적으면 실제 후보 수만 반환합니다.

## 섹션별 정책

| 섹션 | 접근 조건 | 데이터 원천 | 선택·정렬 | 반환 계약 | 캐시·사전 계산 | 재검증·개인화 |
|---|---|---|---|---|---|---|
| 다가오는 여정 | 로그인 및 진행·예정 여정 존재 | 사용자의 여정과 일정 | 현재 또는 예정 여정 중 가장 가까운 1개 | 단건, 없으면 not-found | 없음 | 일정 개수와 기준일 반영 |
| 인기 여행지 | 전체 공개 | 현재 mock, 이후 모집글 집계 | 집계 점수순 5개 | 항목 목록을 포함한 응답 | 실제 집계 전환 시 공통 결과 캐시 | 집계 갱신 시각 제공 |
| 메이트 추천 | 로그인 및 설문 완료 | 사용자별 일일 추천 묶음 | 추천 점수와 저장 순서 | 상태형 응답 | 사용자별 일일 결과 저장 | 현재 게시글·사용자 조건 재검증 |
| 슈퍼호스트 | 전체 공개 | 활성 노출과 게시글 | 무작위 최대 5개 | 목록, 없으면 빈 배열 | 후보 ID를 Redis에 1분 캐시 | 게시글 상태·신고 재검증, 좋아요 반영 |
| 같은 여행지 여행 | 로그인 및 1순위 선호 존재 | 1순위 선호 지역의 모집글 | 오래된 30개 후보 중 무작위 최대 3개 | 목록, 없으면 빈 배열 | 없음 | 공통 노출 조건과 신고 여부 반영 |
| 또래 여행 | 로그인 및 생년월일 존재 | 작성자 나이 차이가 ±5세인 모집글 | 오래된 30개 후보 중 무작위 최대 3개 | 목록, 없으면 빈 배열 | 없음 | 공통 노출 조건과 신고 여부 반영 |

mock 섹션을 실제 데이터로 전환하거나 선택 정책을 변경하면 이 표와 해당 기능 문서를 함께 수정합니다.

## 캐시와 개인화

캐시는 모든 홈 섹션에 일괄 적용하지 않고 다음 기준으로 결정합니다.

- 여러 사용자가 공유할 수 있는 후보나 집계 결과인지 확인합니다.
- 사용자별 결과라면 키 개수, 갱신 주기와 저장 비용을 확인합니다.
- 허용 가능한 데이터 지연과 TTL을 명시합니다.
- 캐시 값 크기와 요청별 전송·역직렬화 비용을 측정합니다.
- 캐시 장애나 miss 시 원본 조회 동작을 정합니다.
- 캐시가 최종 유효성 검사를 대신하는지 명시합니다.

```text
공통 후보·집계 결과
  + 사용자별 제외 조건
  + 사용자별 표시 상태
  = 최종 섹션 응답
```

- 슈퍼호스트는 공통 후보 ID만 캐시하고 신고와 좋아요를 조회 시점에 반영합니다.
- 인기 여행지는 실제 집계 도입 시 공통 순위 결과 캐시를 우선 검토합니다.
- 같은 여행지와 또래 여행은 사용자 조건으로 후보를 좁힐 수 있으므로 병목이 확인되기 전에는 캐시하지 않습니다.

## 정렬과 선택

| 방식 | 적용 기준 |
|---|---|
| 일정순 | 사용자가 가장 먼저 확인해야 하는 시간성 데이터 |
| 최신순 | 새로운 모집글을 우선 보여주는 탐색 섹션 |
| 점수순 | 집계 또는 개인화 점수가 순위를 결정하는 섹션 |
| 무작위 | 자격이 같은 광고 후보에 노출 기회를 분산하는 섹션 |

DB에서 상세 데이터 전체를 조회한 뒤 애플리케이션에서 노출 개수만큼 줄이지 않습니다.
무작위 선택처럼 후보 ID 전체가 필요한 경우에는 후보 수와 선택 비용을 관측하고 확장 계획을 적용합니다.

## 슈퍼호스트 후보 선택과 확장

현재 슈퍼호스트는 다음 순서로 최대 5개를 반환합니다.

1. 노출 기간과 게시글 상태를 만족하는 게시글 ID 목록을 Redis에 1분간 캐시합니다.
2. 요청마다 후보 ID 복사본을 애플리케이션에서 섞습니다.
3. ID를 10개씩 조회하며 현재 노출 상태, 게시글 상태와 신고 여부를 다시 검증합니다.
4. 유효한 카드 5개를 선택한 뒤 로그인 회원의 좋아요 여부를 일괄 조회합니다.

이 방식은 DB의 `ORDER BY RAND()` 전체 정렬을 피하고 캐시 유지 시간 동안 후보 쿼리 반복을 줄입니다.
후보 수를 `N`이라고 할 때 목록 역직렬화, 복사와 셔플은 요청마다 `O(N)`이며 Redis 값 크기와 전송량도 후보 수에 따라 증가합니다.

후보 증가로 운영 기준을 넘으면 다음 순서로 전환합니다.

1. 캐시에 저장할 후보 풀 크기를 제한하고 풀을 주기적으로 교체합니다.
2. 최신 후보만 계속 선택하지 않도록 ID 구간, 노출 시작 시각 구간 또는 이전 풀 제외 방식으로 노출 편향을 확인합니다.
3. 제한된 풀도 부담이 되면 활성 후보를 Redis Set으로 관리하고 `SRANDMEMBER`로 필요한 수만 추출합니다.
4. Redis에서 추출한 뒤에도 현재 상태와 사용자별 신고 조건은 DB에서 검증합니다.
5. 결제 상품 등급이나 노출 보장이 도입되면 무작위 선택과 분리된 가중치·쿼터 정책을 정의합니다.

전환 여부는 후보 개수 하나로 결정하지 않습니다. 캐시 값 크기, Redis 조회 시간, 셔플 시간, 재검증 배치 수, API p95·p99와 JVM 할당량을 함께 확인합니다.

## 운영 지표

모든 섹션은 공통 태그로 응답 시간과 결과 상태를 구분할 수 있어야 합니다.
후보 생성이나 캐시를 사용하는 섹션은 필요한 지표를 추가합니다.

| 지표 | 용도 |
|---|---|
| `section` | 홈 섹션 구분 |
| 응답 시간 | 섹션별 p95·p99 확인 |
| 결과 개수 또는 결과 상태 | 빈 응답과 상태 분포 확인 |
| 예외 유형 | 섹션별 실패 원인 확인 |
| 후보 개수 | 후보 처리 비용 확인 |
| 캐시 hit·miss와 조회 시간 | 캐시 효과와 의존성 확인 |
| 재검증 배치 수 | 오래된 후보와 제외 비율 확인 |

사용자 ID나 게시글 ID처럼 값의 종류가 계속 증가하는 정보는 metric tag로 사용하지 않습니다.
구체적인 계측 구현과 대시보드·경보 기준은 [이슈 #346](https://github.com/ddu-ru/ddu-ru-backend/issues/346)에서 관리합니다.
