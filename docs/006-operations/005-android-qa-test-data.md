# 005. Android QA 테스트 데이터

> 이 문서는 이슈 #350의 Android 통합 QA 데이터를 MySQL 8에 넣고, 검증하고, 안전하게 제거하는 절차를 설명합니다.

---

## 1. 적용 범위

이 데이터는 QA DB에서만 수동 실행합니다. Flyway migration이나 애플리케이션 시작 과정에는 포함되지 않으며, 테스트 데이터용 API와 영구 관리 테이블도 만들지 않습니다.

| 파일 | 역할 |
|---|---|
| `scripts/sql/android_qa_seed.sql` | 상대 날짜 기반 QA 데이터를 생성하거나 기존 QA350 데이터를 원래 상태로 갱신 |
| `scripts/sql/android_qa_cleanup.sql` | QA350 표식 데이터와 가상 사용자 연결 데이터만 FK 역순으로 제거 |

실계정 `userId=1,2,3`은 이미 존재해야 합니다. 세 계정 모두 닉네임, 성별, 생년월일이 있는 프로필을 완료해야 하며, 조건을 만족하지 않으면 시드 실행이 중단됩니다.

시드는 다음 실계정 데이터를 변경하지 않습니다.

- 계정 및 프로필
- 온보딩 및 설문 상태
- 여행 성향
- 여행지 선호와 여행 가능 날짜
- 기존 일반 게시글

단, 새 모집글이 홈 메이트 추천에 반영되도록 세 계정의 **당일 추천 배치만 삭제**합니다. 다음 홈 조회에서 현재 데이터 기준으로 다시 계산됩니다.

---

## 2. 생성되는 데이터

- 가상 사용자 27명: `qa350-user-01@dduru.test`부터 `qa350-user-27@dduru.test`
- 가상 사용자 성별 14:13, 만 21~39세 범위, 고유 닉네임·QA 전화번호, 완료된 온보딩·설문·여행 성향
- 각 가상 사용자의 여행 성향과 일치하는 아바타, `AVATAR` 프로필 이미지 타입, 배경색
- QA 게시글 45개: 모집 가능 30개, 정원 마감 5개, 모집 종료 5개, 여행 종료 5개
- 모든 게시글의 여정, 호스트 멤버십, 그룹 채팅방
- 실계정별 받은 신청 4건과 낸 신청 4건: `PENDING`, `CONTACTING`, `APPROVED`, `REJECTED` 각 1건
- `CONTACTING` 신청의 1:1 채팅방과 양방향 메시지
- `APPROVED` 신청의 활성 여정·그룹 채팅 멤버십
- 실계정별 활성 여정 2개, 좋아요 게시글 6개, 알림 8개
- 실계정이 접근하는 여정 6개의 일정 3개, 공지 2개, 일반 글 4개, 댓글과 이미지
- 읽음, 1개 안 읽음, 여러 개 안 읽음 상태의 채팅방
- 현재 노출 가능한 슈퍼호스트 게시글 5개

게시글 제목과 본문, JSON 태그에는 `[QA350]` 또는 `QA350` 관리 표식이 들어갑니다. 날짜는 `CURDATE()`와 `NOW()` 기준으로 다시 계산되므로 실행일이 바뀌어도 오늘 출발, 마감 임박, 예정 여행을 확인할 수 있습니다.

실계정의 기존 1순위 여행지 선호가 있으면 해당 지역 후보를 3개 이상 배치합니다. 선호가 없는 계정에는 선호 데이터를 새로 만들지 않습니다. 또래 여행 후보는 각 실계정의 생년월일 주변 가상 작성자로 구성합니다. 메이트 추천은 기존 설문이 완료된 실계정에서 바로 확인할 수 있고, 미완료 계정은 앱에서 설문을 완료한 후 확인합니다.

### 실계정별 핵심 시나리오

| 실계정 | 직접 작성한 QA 글 | 승인되어 참여하는 가상 사용자 글 | 낸 신청 4건 |
|---|---|---|---|
| `1` | 제목 끝 `01` | 제목 끝 `06` | 제목 끝 `04`~`07` |
| `2` | 제목 끝 `02` | 제목 끝 `10` | 제목 끝 `08`~`11` |
| `3` | 제목 끝 `03` | 제목 끝 `14` | 제목 끝 `12`~`15` |

각 실계정의 직접 작성 글에는 가상 사용자가 네 상태로 한 명씩 신청합니다. 낸 신청의 상태는 표의 네 게시글 순서대로 `PENDING`, `CONTACTING`, `APPROVED`, `REJECTED`입니다.

## 3. 실행 전 확인

1. 대상이 MySQL 8 기반 QA DB인지 확인합니다.
2. 대상 DB에 현재 `dev`의 최신 Flyway 스키마가 적용되어 있는지 확인합니다. 특히 게시글 동행 유형의 `UNSPECIFIED`와 알림 유형의 `TRIP_UPCOMING`을 지원해야 합니다.
3. 운영 DB가 아닌지 호스트와 DB 이름을 다시 확인합니다.
4. 필요하면 DB 스냅샷을 생성합니다.
5. `userId=1,2,3`의 프로필 필수값을 확인합니다.

```sql
SELECT u.id, u.email, p.nickname, p.gender, p.birthday
FROM users u
LEFT JOIN profiles p ON p.user_id = u.id
WHERE u.id IN (1, 2, 3)
ORDER BY u.id;
```

세 행이 모두 존재하고 `nickname`, `gender`, `birthday`가 모두 채워져 있어야 합니다.

## 4. 시드 실행

저장소 루트에서 실행합니다. 비밀번호는 명령행에 직접 적지 않고 `-p` 프롬프트로 입력합니다.

```bash
mysql --default-character-set=utf8mb4 \
  -h <QA_DB_HOST> -P 3306 -u <QA_DB_USER> -p <QA_DB_NAME> \
  < scripts/sql/android_qa_seed.sql
```

시드는 하나의 트랜잭션에서 실행되고, 임시 매핑 테이블과 이메일·OAuth ID·QA350 표식을 이용합니다. 같은 날 여러 번 실행해도 가상 사용자와 게시글을 중복 생성하지 않고 관리 대상 행을 갱신합니다.

정상 종료 시 사용자, 게시글, 신청, 1:1 채팅방, 실계정 여정, 알림 집계와 실계정별 신청 상태가 출력됩니다. 기본 집계는 다음과 같습니다.

| 항목 | 기대값 |
|---|---:|
| 가상 사용자 | 27 |
| 필수값과 아바타가 완성된 가상 프로필 | 27 |
| QA 게시글 | 45 |
| QA 신청 | 34 |
| QA 1:1 채팅방 | 6 |
| 실계정이 접근하는 활성 QA 여정 | 6 |
| QA 알림 | 24 |

실행 직후 Redis 홈 캐시를 삭제합니다.

```bash
redis-cli -h <QA_REDIS_HOST> -p <QA_REDIS_PORT> \
  DEL 'home:popular-destinations:v1' 'homeSuperHostCandidates::all'
```

Redis 인증이나 TLS를 사용하는 환경에서는 기존 QA 접속 옵션을 함께 사용합니다.

## 5. 앱 검증 순서

1. 홈에서 예정 여행, 인기 여행지, 같은 여행지 동행, 또래 동행, 슈퍼호스트를 확인합니다.
2. 메이트 추천은 설문 완료 계정에서 확인하고, 설문 미완료 계정은 비활성 상태가 유지되는지 확인합니다.
3. 마이페이지에서 작성 글 1개, 낸 신청 4개, 좋아요 6개, 참여 중 여정 2개를 확인합니다.
4. 직접 작성한 모집글의 받은 신청에서 네 상태와 1:1 연락방을 확인합니다.
5. 낸 신청 목록에서 네 상태와 승인된 여정 진입을 확인합니다.
6. 채팅 목록에서 모두 읽음, 1개 안 읽음, 여러 개 안 읽음 방을 확인하고 양방향 메시지를 전송합니다.
7. 각 활성 여정에서 일정, 공지, 일반 글, 이미지, 댓글, 그룹 채팅을 확인합니다.
8. 알림 목록에서 신청 도착, 승인, 여정 공지, 일정, 여행 임박 알림과 읽음/안 읽음 상태를 확인합니다.

정원 마감 글은 호스트와 승인 멤버 수의 합이 `recruit_capacity`와 같고, 모든 QA 글의 `recruit_count`와 `like_count`는 실제 연결 행 수와 일치하도록 생성됩니다.

## 6. 초기화와 정리

시드된 게시글을 앱에서 수정한 뒤 원래 시나리오로 되돌릴 때는 시드를 바로 덮어쓰지 말고 **cleanup → seed → Redis 캐시 삭제** 순서로 실행합니다.

```bash
mysql --default-character-set=utf8mb4 \
  -h <QA_DB_HOST> -P 3306 -u <QA_DB_USER> -p <QA_DB_NAME> \
  < scripts/sql/android_qa_cleanup.sql

mysql --default-character-set=utf8mb4 \
  -h <QA_DB_HOST> -P 3306 -u <QA_DB_USER> -p <QA_DB_NAME> \
  < scripts/sql/android_qa_seed.sql

redis-cli -h <QA_REDIS_HOST> -p <QA_REDIS_PORT> \
  DEL 'home:popular-destinations:v1' 'homeSuperHostCandidates::all'
```

QA 데이터를 완전히 제거할 때는 cleanup만 실행한 뒤 같은 Redis 캐시를 삭제합니다. cleanup은 여러 번 실행해도 안전하며 마지막에 남은 가상 사용자, QA 게시글, 보존된 실계정 수를 출력합니다.

정상 정리 결과는 다음과 같습니다.

| 항목 | 기대값 |
|---|---:|
| 남은 가상 사용자 | 0 |
| 남은 QA 게시글 | 0 |
| 보존된 실계정 `1,2,3` | 3 |

cleanup은 QA350 표식 게시글과 `qa350-user-XX@dduru.test` 계정에 연결된 데이터만 삭제합니다. 실계정의 프로필·설문·여행 성향·선호·기존 일반 게시글은 삭제하지 않습니다.

## 7. SQL 수준 검증 체크리스트

- 시드 첫 실행과 두 번째 실행의 마지막 집계가 같다.
- 가상 사용자 성별이 `F=14`, `M=13`이고 나이가 만 21~39세 범위다.
- 가상 사용자 27명의 전화번호가 모두 채워져 있고 서로 다르다.
- 가상 사용자 프로필의 아바타가 여행 성향의 아바타와 일치하며 배경색이 모두 채워져 있다.
- 게시글 분류가 모집 가능 30, 정원 마감 5, 모집 종료 5, 여행 종료 5다.
- 모든 QA 게시글에 여정, 활성 호스트 멤버, 그룹 채팅방이 있다.
- 실계정별 받은 신청과 낸 신청에 네 상태가 각각 1건씩 있다.
- 모든 `CONTACTING` 신청에 양쪽 사용자가 참여한 1:1 방이 있다.
- 모든 `APPROVED` 신청에 활성 여정 멤버와 그룹 채팅 멤버가 있다.
- 모든 QA 게시글의 모집 인원과 좋아요 수가 실제 연결 행 수와 일치한다.
- 실계정별 좋아요 6개, 활성 여정 2개, 알림 8개가 조회된다.
- 여정 상세 6개마다 일정 3개, 공지 2개, 일반 글 4개가 있다.
- 활성 슈퍼호스트 노출이 5개다.
- cleanup 후 가상 사용자와 QA 게시글은 0개이고 실계정 3명의 기존 상태와 선호가 유지된다.
